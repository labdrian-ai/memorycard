# LongMemEval benchmark

Objective: a public, reproducible benchmark of memorycard on LongMemEval_S, starting with retrieval (recall@k) and later end-to-end QA.
Branch: `feat/longmemeval-bench`. Delivery: ask-on-risk. Test runner: `go test ./...`.

## Specs

- S1. Solve the embedding bottleneck first. The owner said: "lo primero es difinir como vamos a hacr una prueba eficiente cacheando pro contenido o con otro patron para evitar el cuello de botella en el embeddings eso vale la pena que sea el primer punto". Approach accepted with "si dale": a content-addressed cache (key `sha256(model, kind, text)`) as a decorator over `embed.Embedder`, used only by the benchmark. Production code paths are unchanged. A rerun or a resumed run embeds nothing it already embedded.
- S2. Retrieval runner over LongMemEval_S (`xiaowu0162/longmemeval-cleaned`, `longmemeval_s_cleaned.json`). Each question gets a fresh memorycard database built from its own haystack. Granularity is `session` (one memory per session, the current product behavior) or `round` (one memory per user and assistant round). Report recall_any@k and recall_all@k for k = 1, 3, 5 and 10, overall and per question type. Abstention questions (`_abs`) are excluded from retrieval metrics and counted.
- S3. Run a sample of 50 questions with both granularities, then the full set overnight with the winning granularity. The owner chose the sample run with "si dale".
- S5. Hybrid search. The owner said: "si eso te iba a decir el hibrido nos resulta mas beneficioso en resultados pero en recursos que tanto nos aumenta el uso", then "bien entonces vamos para adelante el costo de diseño lo podemos asumir". Dense and BM25 rankings are fused by reciprocal rank fusion (k = 60, a pool of 50 from each). Confidence stays judged on the dense cosine. The mode is opt-in (`Service.SetHybrid`; `-hybrid` in `mc-bench` and `mc-accept`) and the default search is unchanged. It is adopted as the default only if it improves LongMemEval without lowering the 190 private held-out questions.
- S6. Improve memorycard against its own previous results, not against competitors. Originally "beat MemPalace" ("siii esta es la gente que tenemos que superar", "bien tenemos que ir para alla para declarar victoria"); replaced on 2026-10-31 when the owner said: "vamos a enfocarnosen nuestras mejoras mas que en la competencia y declarar victoria el objetivo es mejorarnos a nosotros". The baseline is our own last full 500 run (retrieval any@5 98.1 %, QA 87.0 %); a change counts as an improvement only from a full 500 run, never from the 50-question sample. MemPalace figures already published in the README stay as context.
- S7. Hybrid search reachable from the product. The full 500 with the default dense search gave any@5 93.6, below MemPalace raw 96.6; only hybrid (97.9) beats it. Asked "¿Sumo el modo híbrido como opción del producto antes de publicar?", the owner said "sumalo". `MEMORYCARD_SEARCH=hybrid` turns it on for the CLI and the MCP server; the default stays dense (S5).
- S8. Fix hybrid so it stops hurting Spanish, then end-to-end QA. The owner said: "arreglemos primero el hibrido y despues hacemos el end2end". Hybrid becomes the default only under S5's rule: it improves LongMemEval without lowering the 190 private questions. Choices are made on the gold `dev` split and judged once on `test`, the LongMemEval sample and the full 500. The chosen configuration (L8: lexical pool 10 at weight 0.5, dense top-1 kept first, keyword-overlap boost 0.3 over the title plus the best 1500-char body window, accent folding) lowers gold2 hit@5 by 2 questions (139, 3570); asked whether to accept them, the owner said "las acepto". It becomes the default search; `MEMORYCARD_SEARCH=dense` restores the previous dense search.
- S9. Improve the reader, not retrieval depth (L19: 17 of 22 answerable misses at k = 20 read all their evidence). Asked "¿Arranco a diseñar ese cambio del lector y lo pruebo primero con la muestra de 50?", the owner said "si dalw". `mc-qa -reader careful` adds rules to the official reader prompt for the failures seen at k = 20: prefer the most recent value, list items before counting, write the dates in time arithmetic, decline when the exact thing asked about is never mentioned. `-reader official` (the default) keeps the upstream prompt byte-identical. Tried on the 50-question sample first; it counts as an improvement only from a full 500 run (S6), and results with it are reported as a custom reader, not the official one.
- S10. Held-out evaluation for further reader work. Offered either splitting the 500 into two fixed halves (tune on one, measure on the other) or adding LoCoMo as an independent benchmark, the owner said "Porque no hacer las 2". Split: `mc-qa -split dev|test` keeps a deterministic half of the questions, stratified by question type and abstention, independent of file order; without `-split` all questions run, as today. From now on reader changes are chosen by looking only at `dev` misses and judged once on `test`. The split is not clean: the careful rules (S9) were written looking at all 500. LoCoMo is tracked in `odd/tasks/locomo-benchmark.md`.
- S4. End-to-end QA: the reader and judge model is `gpt-6.1-sol` through Codex. The owner said "y de modelo usemos gpt sol con el proveedor codex" and then "si nosotros vamos a usar gpt-6.1-sol".
